### Q-002 自己テスト「カスタム マッチャー」の失敗の直し方

**Status**

解決済み

**Question**

`text_style_jp.py --test` の「`カスタムマッチャ` → `カスタム マッチャー`」の失敗を、どの方法で直しますか。

**Context**

- **経緯と背景**: テストの期待値は `bin/text_style_jp.py` の 155 行目の `("カスタムマッチャ", "カスタム マッチャー")` で、結果は入力のままです。`.text_style_jp/90_local-katakana.json` には `マッチャ` が 30 行目 (`no_space`) と 130 行目 (`replace`: `マッチャ` → `マッチャー`) の両方にあるため、両者の干渉を疑いましたが、干渉はありませんでした。
- **根本原因**: 処理は 2 段階です。(1) 分割前の `replace` は、カタカナの語の両端が非カタカナの場合だけ適用されます (`_replace_skip_existing` の `require_boundary`)。`カスタムマッチャ` は `マッチャ` がカタカナ列の途中にあるため適用されません。(2) その後 SudachiPy が複合語を分割し、分割後の `replace` が `マッチャ` → `マッチャー` を適用します。ところが、手元の `sudachidict-core` 20261015 は `カスタムマッチャ` を未知語 (`is_oov()` が真) の 1 語として返し、分割しません。そのため (2) に届きません。`チャンネルポインタ` は既知語の `チャンネル` と `ポインタ` に分割されるため、同じ流れでテストが成功します。
- **干渉がないことの根拠**: `no_space` と `replace` の両方に属する語は、`load_dictionaries()` が `no_space` の保護から外します (`final_no_space`)。`_no_space_set` に `マッチャ` は含まれないことを確認しました。30 行目の項目は効いていません ([Q-003](#q-003-no_space-と-replace-の両方にある語の扱い))。
- **確認した事実**: 分割結果は辞書の版に依存するため、このテストは辞書が更新されると結果が変わります。`イベントマッチャ` のような他の複合語も同様に検出されません。

```text
$ python3 bin/text_style_jp.py --dry-run m.md   (m.md は 1 行ずつ別の段落)
カスタムマッチャ    -> 指摘なし (期待: カスタム マッチャー)
カスタム マッチャ   -> 3:1 "マッチャ" → "マッチャー" dict-replace
```

- **案 A**: `add_space` に `カスタム マッチャー` を追加します。`add_space` は連結形 (`カスタムマッチャ`、`カスタムマッチャー`) も表記ゆれとして検出し、`カスタム マッチャー` へ直します。作業用の複製で追加して `--test` が全件成功することを確認しました。Microsoft の規則では `カスタム` と `マッチャー` の 2 語のため空白を入れる扱いで、既存の `カスタム ハンドラー` (79 行目) と同じ形です。
- **案 B**: 辞書は変えず、自己テストの例を Sudachi が分割できる複合語へ差し替えます。例: `チャンネルポインタ` の例とは別に、`replace` が分割後に効くことを示す語を選びます。ただし分割の可否は辞書の版に依存し続けます。
- **案 C**: 自己テストで `replace` の見出し語の適用だけを検証するよう、分割に依存しない入力 (例: `カスタム マッチャ`) へ変えます。分割後の適用を確認する目的は `チャンネルポインタ` の例が担います。

```text
/* 案 A: 90_local-katakana.json の add_space に 1 行追加 */
"カスタム マッチャー",

/* 案 C: テストの期待値 */
("カスタム マッチャ", "カスタム マッチャー"),
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) `add_space` に `カスタム マッチャー` を追加し、テストの期待値は変えない
- [ ] B: テストの例を、Sudachi が分割できる別の複合語へ差し替える
- [ ] C: テストの入力を `カスタム マッチャ` (空白あり) へ変える
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

**Assessment**

確認済み。単一選択で A が選ばれています。作業用の複製 (セッションの一時ディレクトリ) で `add_space` に `カスタム マッチャー` を追加し、`text_style_jp.py --test` が全件成功することを再確認しました。SudachiPy を無効にした状態でも `カスタムマッチャ` と `カスタム マッチャ` はどちらも `カスタム マッチャー` になり、結果は Sudachi 辞書の版と有無に依存しません。CI の Linux コンテナー (`/home/user/oracle-linux-container` の `src/Dockerfile`) は SudachiPy を事前導入せず、初回実行時に `pip install --user` で最新版を導入します。2026-11-25 の CI (run 45552671556、ol9) のログでは sudachipy 0.7.0 と sudachidict-core 20261015 で、手元と同じ版でした。`カスタム` と `マッチャー` は原語 (custom matcher) の 2 語に対応するため、空白を入れる形は Microsoft の規則に準じるローカル辞書の方針と一致します。`イベントマッチャ` など、ほかの未知語の複合語は引き続き検出されません。これは `docs/text_style_jp.md` に記載済みの仕様 (Sudachi が分割できない語は `add_space` で補う) の範囲です。

### Q-004 test_livedocs_path_spaces の失敗の直し方

**Status**

**Question**

`test_make_livedocs_with_complete_system_environment` の失敗を、どの方法で直しますか。

**Context**

- **経緯と背景**: このテストは、システム Python が livedocs の依存をすべて満たす場合に venv を作らないことを確認します。失敗したのは、この環境のシステム Python の依存が、採用範囲を満たしていないためです。テストの前提が成り立たない環境で実行されています。
- **システム環境の判定条件**: `livedocs/bin/resolve_python_components.py` の `select_python()` は、`livedocs/requirements-compatible.txt` の範囲を満たさないパッケージを不足とみなします。手元の Python 3.12 (`/usr/bin/python3`) で判定すると、不足は次の 2 件でした。

Table: システム Python の依存と採用範囲の対応

| パッケージ | 手元の版 | 採用範囲 | 判定 |
| --- | --- | --- | --- |
| pymdown-extensions | 13.1 | `>=11.0.2,<12.0.0` | 範囲外 |
| watchdog | 7.1.0 | `>=6.0.0,<7.0.0` | 範囲外 |
