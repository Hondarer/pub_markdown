# 日本語技術文書の作成と推敲

`framework/docsfw/docs/japanese-technical-writing-guideline.md` の対象となる構成と執筆、段落、読みやすさと文構造、表現、推敲と確認の各節を参照してください。

## 執筆前の構成設計 (生成時制約)

文章の質は、書き終えてから直すよりも、執筆前の構成設計と生成時の制約によって保ちます。

- **結論先行と前置きの排除**: 自明な前提や「本稿では〜」といった宣言から入らず、タイトルや最初の一文で結論・主メッセージを示します。
- **中身を伝える見出し (スケルトン)**: 単なる名詞ラベル見出しを避け、見出しに結論や要点を埋め込み、見出しの拾い読みだけで論旨が通る骨組みを作ります (ただし同一書式で画一化しない)。
- **因果と経緯の地の文化**: 理由や因果関係を箇条書きに逃げず、接続表現を用いた地の文で記述します。箇条書きは真に並列な要点圧縮に限定します。
- **専門用語の導入順序**: 機能や現象を平易に説明してから名前 (ラベル) を渡します (機能 → 名前)。
- **具体例と実数による接地**: 抽象論を避け、固有名詞、実数、具体例で裏付けます。

## 推敲と自己点検

推敲時は、「検出は機械、判断は文脈」の原則に従い、機械的な一律置換を避けて文脈に応じた判断を行います。

- **脱 AI 臭と文体の自然さ**: 結論の押し付けやまとめ口調 (「〜と言えるでしょう」)、過剰な強調、空疎な接続語、予防線、プレゼン的数宣言 (「理由は 3 つあります」)、決め台詞、無生物主語、翻訳調構文 (「〜することができる」「〜という観点から」) を目視で確認し排除します。
- **情報密度と簡潔さ**: 自明な講釈や言い換えによる水増しを削ぎ落とします。冗長性の排除では文字数や文数だけで判断せず、動機、対象、操作、因果、条件を読者の推論に委ねる安易な短文化を避けて必要な記述を残します。
- **文構造と可読性**: 語順の原則 (長い修飾語を先に)、読点の原則 (統語的切れ目・修飾逆順のシグナル)、一文一義と主語述語の近接、接続詞の適切な射程を確認します。
- **文体と整形**: 本文段落のです・ます調、一文一行、イ形容詞終止＋「です」の排除、文末表現の単調な連続回避を適用します。

重複を整理する場合も依頼された範囲に限定し、他の文書の再構成は必要性がある場合に限ってください。  
外部由来の配布物 (外部 OSS や第三者ライブラリなど) や自動生成成果物は対象外とします。自動生成成果物に問題がある場合は直接編集せず、生成元 (スクリプトやテンプレートなど) を対策してください。  
複数ファイルの一括推敲 (バッチ処理) を行う場合は、全文章を確認するため相応のトークンを消費します。バッチ処理の着手前に 1 回のみトークン消費の旨をユーザーに確認してください。  
翻訳や UI 表記の固有判断が必要なら `understand-japanese-docs-style` を参照してください。

Markdown を変更した場合は、変更ファイルへ `text_style_jp.py --dry-run` を実行し、不自然な変換がなければ `--in-place` を実行してください。  
会話内の回答やレビューだけの場合は、ファイルの作成や整形コマンドの実行を必要としません。

自身が Antigravity CLI ではなく、かつ `agy` (Antigravity CLI) が利用可能な環境である場合は、Antigravity CLI を利用して Gemini 系の最新モデルでこの作業を行ってください。
