# 日本語文書のレビューと推敲

Markdown 文書、ソース コードのコメント、メッセージ文字列などの日本語をレビューし、自然な言い回しへ推敲します。  
詳細な表現規範は `framework/docsfw/docs/japanese-technical-writing-guideline.md` の表現と確認の節を参照してください。

## 実行環境とモデルの選定

自身が Antigravity CLI ではなく、かつ `agy` (Antigravity CLI) が利用可能な環境である場合は、Antigravity CLI を利用して Gemini 系の最新モデルでこの作業を行ってください。

## 対象範囲と着手前の確認

対象ファイル (`.md` 文書、ソース コードのコメント、リソース定義など) や、特定ディレクトリ配下を再帰的に走査するかどうかについて、ユーザーから明示的な指定がない単独起動では、変更を開始する前に対象範囲と対象種別をユーザーとすり合わせてください。  
外部由来の配布物 (外部 OSS や第三者ライブラリなど) や、ビルド・ツールにより自動生成された成果物は推敲の対象外とします。自動生成された成果物に問題がある場合は、成果物を直接編集せず、その生成元 (生成スクリプト、テンプレート、元データなど) を対策してください。  
複数ファイルの一括推敲 (バッチ処理) を行う場合は、全文章を網羅的に確認するため相応のトークンを消費します。バッチ処理の着手前に 1 回のみトークン消費の旨をユーザーに確認してください。

## 推敲の原則

原文の意図や内容を変えずに、極めて自然かつ平易なビジネス ユースの日本語へ修正します。  
数字、固有名詞、コード識別子、断定の強さは変更しないでください。  
規範や本スキルに示す言い換えは代表例であり、表面的な語句置換にとどまらず、その考え方を用いたうえで 1 ファイルずつの全文章確認を行ってください。

推敲時は次の観点を確認してください。

- 口語表現や擬人化表現 (「抱え込む」「口」「手書き」「歯抜け」など) を客観的・具体的な記述へ置き換えます。
- システムの振る舞いや操作に関する日常会話の動詞や口語名詞を、客観的な技術表現へ置き換えます。
    - 「呼ぶ」→「呼び出す」
    - 「見る」→「参照する」「確認する」「監視する」
    - 「書く」→「記述する」「定義する」「書き込む」
    - 「出す / 出る」→「出力する」「発行する」「送出する」「生じる」
    - 「消す / 消える」→「削除する」「破棄する」「初期化する」
    - 「落ちる」→「異常終了する」「クラッシュする」「失敗する」
    - 「走る」→「実行される」「動作する」
    - 「飛ぶ」→「遷移する」「ジャンプする」
    - 「使い回す」→「再利用する」「共通化する」
    - 「無い」→「存在しない」「設定されていない」「定義されていない」
    - 「足す」→「追加する」「付与する」
    - 「選ぶ」→「選択する」
    - 「置く」→「配置する」「格納する」
    - 「引く」→「取得する」「参照する」「検索する」
    - 「決める」→「決定する」「確定する」
    - 「勝つ」→「優先される」
    - 「触る / 触れる」→「アクセスする」「直接参照する」「変更する」
    - 「捨てる / 落とす」→「破棄する」「除外する」「解放する」
    - 「食い違う」→「不整合が生じる」「一致しない」
    - 「詰め直す」→「再配置する」「詰め替える」
    - 「ズレ」→「不整合」「乖離」
- 長音符号や送り仮名、表記揺れを統一します。
    - 「既定値」「既定の」 (×「デフォルト」)
    - 「切り替え」 (×「切替」「切替え」)
    - 「フィルター」 (長音を省略した表記を避ける)
    - 「期待どおり」 (×「期待通り」)
    - 「次のとおり」 (×「以下の通り」「下記のとおり」)
- 「ダミー」表現はテスト用ファイル等の文脈上必要な場合に限定し、安易な仮置き表現を避けます。
- 文末の「〜こと」の過剰な連続を抑え、通常の文体へ整えます。
- 見出しにおける口語調や願望・主観的表現 (「〜が楽になる」「〜が速くなる」「〜が強くなる」など) を、「〜性の向上」「〜の迅速化」「〜の強化」などの客観的な名詞句へ整えます。
- 同一のリストや表の内部では文体を統一し、項目ごとにです・ます調と常体を混在させません。
- 業界標準の技術用語を優先し、方言的な造語 (「添字」「添字引き」など) を避け、「インデックス」「インデックス参照」などへ統一します。
- 状態や代替動作 (「欠けている」「読み替える」など) を曖昧にせず、「未設定」「未定義」「フォールバックする」「代替として使用する」と明記します。

## 変更後の確認

Markdown ファイルを変更した場合は、対象ファイルごとに `text_style_jp.py --dry-run` を実行し、問題がなければ `--in-place` を実行してください。  
ソース コードのコメントやメッセージ定義を変更した場合は、ビルドやテストを実行し、構文エラーや振る舞いへの影響がないことを確認してください。  
レビューや提案だけの依頼ではファイルを変更せず、推敲案を提示して確認を求めてください。
